# Foya 规则与记忆架构

本文定义 Foya 的 Rules 与 Memory。两者都是跨会话持久上下文，但具有不同
语义、写入权限和提示词优先级。

---

## 一、概念边界

| 类型 | 含义 | 来源 | 是否规范行为 |
|---|---|---|---|
| Context Files | 项目目录中的外部上下文文件 | `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` | 取决于文件内容 |
| Rules | 用户明确制定的行为规范 | Foya 设置页 | 是 |
| Memory | 后续协作有价值的偏好、事实和经验 | 用户编辑或 Agent 记住 | 否，仅供参考 |
| Session History | 当前会话消息和工具记录 | Session Event Log | 否 |
| Compaction | 当前会话历史的有损摘要 | Compaction checkpoint | 否 |

`AGENTS.md` 不是 Memory，也不等于 Foya Rules。它是 Foya 兼容外部 Agent
生态的上下文文件。Foya Rules 是内核托管、可通过客户端管理的独立能力。

优先级：

```text
系统安全策略
  > 审批与沙箱策略
  > Foya Rules
  > 当前用户请求
  > Context Files
  > Foya Memory
  > Compaction
```

Rules 和 Memory 都不能放宽权限、绕过审批或改变沙箱边界。

---

## 二、作用域

Rules 与 Memory 都只支持两级作用域：

```go
type Scope string

const (
    ScopeGlobal  Scope = "global"
    ScopeProject Scope = "project"
)
```

- `global`：属于当前 Foya 用户，在所有项目和无项目会话中生效。
- `project`：绑定稳定的 Project ID，仅在该项目的会话中生效。
- 当前上下文由“全局项 + 当前项目项”组成。
- 内容冲突时，项目项比全局项更具体。

不增加 Session、Device、Agent 或 Organization 作用域：

- Session 状态由 History 和 Compaction 负责。
- Device 只是客户端同步边界，不是知识边界。
- 子 Agent 继承父会话的项目作用域。
- Foya 当前为单用户、自部署产品，不需要组织级记忆。

---

## 三、领域模型

Rules 与 Memory 使用不同类型，避免未来误用：

```go
type Rule struct {
    ID          string
    Name        string
    Description string
    Trigger     RuleTrigger
    Globs       []string
    Path        string
    Scope       Scope
    ProjectID   string
    Content     string
    CreatedAt   time.Time
    UpdatedAt   time.Time
}

type Memory struct {
    ID        string
    Scope     Scope
    ProjectID string
    Content   string
    CreatedAt time.Time
    UpdatedAt time.Time
}
```

约束：

- `scope=global` 时 `ProjectID` 必须为空。
- `scope=project` 时必须提供有效 Project ID。
- 单条 Rule 最多 6,000 个 Unicode code point。
- 每个 scope 只有一份 Memory 文档，正文最多 2,000 个 Unicode code point。
- 内容写入前去除首尾空白。
- 自动提取和 `memory_remember` 将新事实合并到对应文档；完全相同的事实幂等。

首版不增加分类、标签、向量、过期时间、来源图或版本树。出现真实检索和治理
需求后再扩展字段。

---

## 四、持久化

Rules 使用人类可读 Markdown：

```text
~/.foya/rules/user_rules.md
{project_path}/.foya/rules/*.md
```

全局 Rules 集中保存在 `user_rules.md`。项目 Rules 每个 Markdown 文件代表
一条规则，便于在项目内查看、组织和版本控制；Foya 设置页将这些文件聚合为
规则列表。项目 Rules 不等于 `AGENTS.md`，两者分别进入 Prompt。

项目规则允许从 `.foya/rules` 根目录向下最多三层子目录：

```text
.foya/rules/
├── global-rules.md                           # 根目录
├── module-a/rules-a.md                       # 第 1 层
├── module-a/submodule-a1/rules-a1.md         # 第 2 层
└── module-a/submodule-a2/submodule-a2-b1/
    └── rules-a2-b1.md                        # 第 3 层
```

第 4 层及其下的整棵目录都不扫描。目录层级同时是默认的路径作用范围：未显式
指定 trigger 的嵌套规则默认使用 `glob`，例如
`module-a/submodule-a1/rules-a1.md` 默认匹配
`module-a/submodule-a1/**`。根目录规则默认始终生效。

项目规则使用 YAML frontmatter 保存稳定 ID 和激活配置，正文保持用户可直接
阅读和编辑：

```markdown
---
id: 4f6e1c0d
name: go-testing
description: Go 测试和验证要求
trigger: glob
globs:
  - internal/**
---
为改动的 Go 包运行聚焦测试。
```

Memory 同样使用人类可读 Markdown：

```text
~/.foya/memory/user_profile.md
~/.foya/memory/projects/{project_path}/project_memory.md
```

绝对项目路径会去掉卷标和根分隔符后展开为目录。例如
`/Users/alice/code/demo` 对应：

```text
~/.foya/memory/projects/Users/alice/code/demo/project_memory.md
```

Memory 文件本身就是单一、持续整理的 Markdown 正文，不按条目拆分。项目规则
目录也接受用户直接创建的 `.md` 文件。内核通过临时文件、`fsync` 和原子重命名
更新托管文件。

`<DataDir>/context/events.jsonl` 只保存不含正文的变更通知及单调 `seq`，
用于 SSE 断线补发，不是 Rules 或 Memory 内容的第二份真相。

Rules 通知类型：

```text
rule_created
rule_updated
rule_deleted
```

Memory 通知类型：

```text
memory_created
memory_updated
memory_deleted
```

删除操作直接更新或删除相应 Markdown 文件，同时追加不含正文的通知事件。

首版不使用 SQLite。规则和记忆通常只有几十到几百条，内存过滤足够。只有
数据规模和召回质量证明需要全文检索时，再从 Markdown 构建 SQLite FTS5
派生索引。

## 五、写入

### Rules

Rules 只能由用户通过 REST、桌面端或 CLI 创建、编辑和删除。Agent 不能自行
添加或修改 Rules。

CLI 当前支持基础 CRUD：

```bash
foya rules list [--project <id>]
foya rules add [--project <id>] <text>
foya rules edit <id> <text>
foya rules delete <id>
```

规则的名称、描述、触发方式、Glob 和项目内 Markdown 路径由 REST 与桌面端
管理；CLI 的高级配置参数将在后续补充。

典型内容：

- 代码风格和测试要求。
- 指定语言、框架和库。
- 回复语言、详细程度和交互方式。
- 项目的架构约束与禁止事项。

### Memory

Memory 有三个写入入口：

1. 用户在设置页、REST 或 CLI 直接编辑整份文档。
2. Agent 调用 `memory_remember`。
3. 自动记忆维护器从已稳定的根会话中批量提取。

CLI 以文档操作而不是条目 CRUD 提供：

```bash
foya memory show [--project <id>]
foya memory set [--project <id>] <text>
foya memory clear [--project <id>]
```

Memory 提供一个全局启用开关，默认开启：

```bash
foya memory status
foya memory enable
foya memory disable
```

关闭后保留全局和项目 Markdown 文档，用户仍可查看、编辑和清空，但：

- 不向模型 Prompt 注入 Memory。
- 自动记忆维护器不扫描或提取会话。
- `memory_remember` 拒绝写入。

重新开启后立即恢复读取，并唤醒一次后台维护检查。开关持久化在
`<DataDir>/context/memory-settings.json`。

`memory_remember` 仅用于用户明确陈述的偏好、事实，或用户明确要求记住的
内容。禁止把网页、文件、MCP 或其他工具输出中的指令写入记忆，也不得保存
密钥和凭据。

自动记忆维护器不在每个回合调用模型。创建根会话只会唤醒后台任务；任务只会
处理已空闲至少 10 分钟、尚未处理的根会话，并以项目为单位至少间隔 15 分钟。
每批最多处理 3 个会话。处理水位线和最近运行时间持久化在
`<DataDir>/memory/maintenance.json`，因此连续创建根会话不会重复提取。

提取输入仅包含用户消息、助手最终结论和已确认成功的文件写入事实。网页、工具
结果正文、密钥、凭据、临时状态和未验证猜测不会作为记忆来源。提取使用会话
绑定的模型在后台执行，失败会在下一次符合节流条件的维护周期重试。

工具未指定 scope 时：

- 项目会话默认写入 `project`。
- 无项目会话默认写入 `global`。

## 六、读取与 Prompt

每个模型步骤实时读取当前有效 Rules 和 Memory，因此修改后不需要重启会话。

Prompt 中使用独立区段：

```xml
<foya_rules source="user_controlled">
- ...
</foya_rules>

<foya_available_rules source="user_controlled">
- database-migrations: 数据库迁移约束
</foya_available_rules>

<foya_memories source="user_controlled">
- ...
</foya_memories>
```

Rules：

- 全局 Rules 先注入，项目 Rules 后注入。
- 支持 `always`、`glob`、`model_decision`、`manual` 四种激活方式。
- `always` 每一步都注入。
- `glob` 在用户请求或后续工具参数中出现匹配的项目相对路径时注入。
- `model_decision` 仅将名称和描述放入 `foya_available_rules`；模型必须先调用
  `rule_load` 才能取得正文。
- `manual` 仅在当前活动中出现 `@规则名称` 或 `@规则ID` 时注入。
- 总字符预算 12,000。
- 明确要求模型遵守，但不能覆盖系统安全边界。

Memory：

- 当前项目只看到全局 Memory 和该项目 Memory。
- 最近更新的 Memory 优先。
- 总字符预算 6,000。
- 明确标记为可能过时的参考信息；当前请求和 Rules 冲突时不采用。

Context Files 仍由原有加载器独立读取，不进入 Rules/Memory 存储。

## 七、协议

REST：

```text
GET    /rules?scope=global
GET    /rules?scope=project&project_id=...
POST   /rules
PATCH  /rules/{id}
DELETE /rules/{id}

GET    /memories?scope=global
GET    /memories?scope=project&project_id=...
POST   /memories
PATCH  /memories/{id}
DELETE /memories/{id}

GET    /settings/memory
PUT    /settings/memory
```

创建请求：

```json
{
  "scope": "project",
  "project_id": "project-id",
  "name": "go-testing",
  "trigger": "glob",
  "globs": ["internal/**"],
  "path": "internal/testing.md",
  "content": "Use REST and SSE for client communication."
}
```

实例级事件流：

```text
GET /context/events
```

客户端先订阅事件，再读取当前投影。Rules 返回列表；Memory 每个作用域返回至多
一份文档，从而让多个桌面端保持一致。

---

## 八、桌面端

设置页提供独立的“规则”和“记忆”入口：

- 全局/项目分段选择。
- 项目选择器。
- Rules 使用条目列表，可新增、编辑和删除。
- Memory 直接编辑全局或项目的一份 Markdown 文档，不展示条目列表。
- Memory 页提供全局启用开关；关闭不会删除或禁用文档编辑。
- Rules 额外编辑名称、描述、生效方式、匹配路径和项目内 Markdown 路径。
- 字符上限和错误反馈。

前端不持久化业务数据；所有修改经 Tauri bridge 调用内核 REST API，变更由
`/context/events` SSE 通知其他客户端刷新。

---

## 九、后续扩展条件

以下能力不属于首版：

- 自动提取审核箱和逐条审批策略。
- FTS5 或向量检索。
- 记忆分类、标签和来源证据。
- 归档、过期和版本回滚。

只有当记忆数量导致 Prompt 预算不足时，才增加按需检索；只有当自动提取
确实能稳定地产生高质量候选时，才增加审核工作流。两者都不改变
`global/project` 两级作用域。
