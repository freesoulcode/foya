# Foya 节点抽象设计

本文给出 Foya 内核各核心节点的抽象设计:职责 + Go 抽象接口 + 与其他节点的咬合点。接口用 Go 表达,标注职责描述 + 代码名。这是接口层骨架,尚未到字段级详细设计。

配套文档:[架构.md](./架构.md)。

---

## 节点归位

这些节点不是平级的,分属不同层次:

| 节点 | 归属 | 本质 |
|---|---|---|
| Agent Loop | 内核骨架 | 驱动回合的引擎 |
| Channel / Broker | 内核骨架 | 事件流总线 |
| 工具 Tool | 内核骨架 | 模型可调用的执行单元 |
| 审批 Approval | 内核骨架 | 工具执行前的门 |
| Hooks | 内核骨架 | 生命周期切面 |
| 沙箱 Sandbox | 能力约束 | 工具执行的隔离层 |
| Agent Definition | 静态配置 | 用户级/项目级智能体定义 |
| 子 Agent | 能力(工具) | 独立 Child Session 中的一次委派 |
| 多 Agent Scheduler | 控制面 | 并发、预算、取消与父子谱系 |
| Computer Use | 能力(客户端侧) | 屏幕操作工具集 |
| 记忆 Memory | 上下文来源 | 跨会话持久事实 |
| 技能 Skills | 上下文来源 | 按需加载的指令包 |
| 命令 Commands | 客户端交互 | 用户触发的快捷动作 |
| 规则 Rules | 上下文来源 | 常驻约束注入 |

公共咬合:所有能力**都以 Tool 的形态被模型调用**,所有事件**都以 Event 的形态经 Channel 广播**。

## Agent Loop(回合引擎 AgentLoop)

职责:驱动「组装上下文 → 请求模型 → 解析工具调用 → 执行 → 回灌 → 判断是否继续」的单回合循环。回合是可取消的后台 goroutine,主循环永远能响应中断。

```go
// 一个回合任务，可被取消
type Turn interface {
    Run(ctx context.Context, in TurnInput) (TurnResult, error)
    Kind() TurnKind // Regular / Compact / SubAgent ...
}

// 回合引擎：每 session 串行，多 session 并发
type AgentLoop interface {
    // 提交一个回合；同 session 若在跑，按 QueueMode 排队或抢占
    Submit(sessionID string, in TurnInput) (runID string, err error)
    Cancel(sessionID string)             // 取消当前回合
    Steer(sessionID string, msg Message) // 运行中插话
}

type TurnResult struct {
    NeedsFollowUp bool // 模型还要继续调工具 → 再跑一轮
    LastMessage   Message
    StopReason    StopReason // Stop / ToolCalls / Length / Error / Aborted
}
```

咬合:循环体内每步向 Channel 发事件、调 Provider 取流、经 Approval 过工具、调 Tool 执行、超限时触发 Compaction。终止条件:`!NeedsFollowUp` 或收到取消或 stop-hook 阻塞。

## Channel / Broker(事件总线 Broker)

职责:内核内部的发布订阅,把内核事件扇出给多个订阅者(多客户端订阅同一会话)。两级投递区分「有损高频」与「必达终止」。

```go
type Broker[T any] interface {
    Subscribe(ctx context.Context) <-chan Event[T] // 每订阅者独立 buffered channel
    Publish(topic string, ev Event[T])             // 有损:buffer 满即丢(token 增量)
    PublishMustDeliver(ctx context.Context, topic string, ev Event[T]) error // 必达:有界阻塞+超时
}

type Event[T any] struct {
    Seq     uint64 // 单调序号 → SSE 断线补发 + 多设备续接
    Type    EventType
    Payload T
}
```

咬合:AgentLoop 是生产者,协议层 SSE 编码器是消费者。序号 `Seq` 是「日志即真相」和「Last-Event-ID 补发」的公共锚点。子 agent 之间通信也走它——父子 agent 各自是 topic 上的收发方。

## 工具(Tool + ToolRegistry + ToolRouter)

职责:声明喂给模型的 schema、路由模型的调用到 handler、执行并结构化回灌。

```go
type Tool interface {
    Name() string
    Spec() ToolSpec         // JSON Schema，喂给模型
    Exposure() ToolExposure // Direct / Deferred(延迟加载省 token) / Hidden
    Run(ctx context.Context, call ToolCall) (ToolResult, error)
}

type ToolRegistry interface {
    Register(t Tool)         // 内置工具
    RegisterExternal(t Tool) // MCP/动态工具，可去重
    Get(name string) (Tool, bool)
}

type ToolResult struct {
    Content   []ContentPart // 文本/图片/artifact 引用
    IsError   bool          // 失败也回灌给模型自我修正
    Terminate bool          // 该批次是否提前结束回合
}
```

咬合:Registry 生成 model-visible schema 列表;Router 把模型返回的 call 转 ToolCall 分派;Run 前经 Approval + Hooks,执行落在 Sandbox 内。`Exposure=Deferred` 实现「按需加载 schema」。

## 审批(ApprovalGateway)

职责:工具执行前决定自动放行/问用户/拒绝。内核内部同步阻塞,对外表现为「SSE 出请求 + REST 回决策」的异步对。

```go
type ApprovalGateway interface {
    // 工具内部就地调用；内部阻塞等 UI 回决策
    Request(ctx context.Context, req ApprovalRequest) (Decision, error)
    // 客户端经 REST 回执，按 requestID 解除阻塞
    Resolve(requestID string, d Decision) // Take 语义:只有第一个生效
}

type Decision int // AutoApprove / Approved / ApprovedForSession / Denied

// 三态判定:档位 × 沙箱 → 结果
type Policy interface {
    Assess(action Action, mode ApprovalMode, sb SandboxProfile) SafetyCheck
    // SafetyCheck: AutoApprove / AskUser / Reject
}
```

咬合:`Request` 内部用 channel 阻塞,`Resolve` 从 pending map 原子取出 channel 写回(解决多端竞争)。请求经 Broker 必达广播给所有客户端,故手机批、桌面同步。档位 `ApprovalMode` = explore/ask/bypass。

多端协同示例:agent 请求确认命令 → 事件广播到桌面和手机两端 → 任一端 `POST /permissions/{id}` 批准 → 内核解除阻塞并广播「已批准」→ 另一端确认框自动消失。谁点、哪个设备点都不重要(单用户),靠 requestID 关联,靠序号补发容错。

## 沙箱(Sandbox)

职责:约束工具执行的副作用爆炸半径。把原始命令改写成「隔离包装后的命令」,跨平台。

```go
type Sandbox interface {
    // 把 argv 改写成沙箱包装后的 argv
    Wrap(req ExecRequest, profile SandboxProfile) (ExecRequest, error)
    Kind() SandboxKind // None / MacSeatbelt / LinuxLandlockSeccomp
}

type SandboxProfile struct {
    FileSystem    FSAccess // read / project-write / full
    WritableRoots []string
    Network       NetworkAccess
}
```

咬合:被内核侧能力(bash/edit)的执行路径调用。本地桌面场景 MVP 可先 `None` + 审批兜底;云端自部署时必须启用(Linux landlock/seccomp)。是能力的约束层,不是能力本身。

## Hooks(HookRuntime)

职责:在生命周期关键点插入切面——工具执行前后、压缩前后、回合起止。可拦截/改写/阻塞。

```go
type HookRuntime interface {
    Run(ctx context.Context, point HookPoint, payload HookPayload) HookOutcome
}

type HookPoint int // PreToolUse / PostToolUse / PreCompact / Stop / SessionStart ...

type HookOutcome struct {
    Block   bool         // 阻止该动作
    Halt    bool         // 中止整个回合
    Mutated *HookPayload // 改写输入(如重写工具参数、预批准权限)
}
```

咬合:AgentLoop 在各阶段调用;PreToolUse 可预批准权限(绕过 Approval)、可 deny;是工具装饰器的实现基座——每个工具包一层 hookedTool。用户自定义扩展点。

## Agent Definition(静态智能体定义)

职责:声明可复用智能体的角色、系统指令、模型、工具面和执行预算。定义本身不运行,启动时解析成不可变快照并绑定到 Child Session。

发现位置:

```text
用户级：$HOME/.agents/agents/{name}.md
项目级：{workspace}/.agents/agents/{name}.md
```

Markdown 正文是角色指令,YAML frontmatter 可声明 `name`、`description`、`model`、`tools`、`max_turns` 和 `timeout`。项目级定义优先于同名用户级定义;调用方也可用完整 ref 显式选择作用域。

```go
type AgentDefinition struct {
    Ref          string
    Name         string
    Description  string
    Scope        AgentScope // builtin / user / project
    Model        string
    Tools        []string
    Instructions string
    MaxTurns     int
    Timeout      time.Duration
    Digest       string
}

type AgentRegistry interface {
    List(ctx context.Context, projectID, projectPath string) ([]AgentDefinition, error)
    Get(ctx context.Context, projectID, projectPath, refOrName string) (AgentDefinition, error)
}
```

安全约束:项目必须先由用户注册;定义只能缩小工具面,不能扩展父会话权限;全部 Agent 控制工具会从 Child Session 工具列表中移除,默认禁止递归派工。

## 子 Agent(SubAgent)

职责:主 Agent 通过 `spawn_agent` 异步创建隔离任务,用 `wait_agents`、`read_agent_output`、`cancel_agent` 和 `list_agents` 控制执行。同步 `agent` 保留为兼容入口。未指定 Agent Definition 时使用内置通用分析角色。

```go
type SpawnAgentRequest struct {
    ParentSessionID  string
    ParentToolCallID string
    Task             string
    AgentRef         string // 可选
    Context          ContextSelection
}

type AgentResult struct {
    Status         AgentStatus
    ChildSessionID string
    AgentRef       string
    AgentName      string
    Output         string
    Error          string
}
```

每个子 Agent 是正式 Child Session,拥有独立上下文窗口、事件流、压缩状态和取消信号。Child Session 持久记录:

```text
parentSessionId
spawnedBy.parentRunId
spawnedBy.parentTurnId
spawnedBy.parentToolCallId
agentRef
agentDigest
```

过程事件保留在 Child Session,父会话收到 `queued/running/started/completed/failed/cancelled/interrupted` 生命周期事件。客户端订阅 Child Session SSE,按 `parentToolCallId` 在父会话内实时展示 reasoning、工具调用和输出。

上下文不会隐式复制整个父窗口。调用方显式选择 `none`、`selected`、`summary` 或 `last_n_turns`,内核构造带任务目标和父消息引用的结构化任务包。

## 多 Agent Scheduler(并发控制)

职责:控制并发槽位、取消传播和任务树预算。第一阶段采用父 Agent 自主派工,不引入声明式 DAG 或 Agent 自由邮箱。

```go
type AgentScheduler interface {
    Start(ctx context.Context, req SpawnAgentRequest) (AgentRunSnapshot, error)
    Wait(ctx context.Context, ids []string, all bool) ([]AgentRunSnapshot, error)
    Read(runID string) (AgentRunSnapshot, error)
    Cancel(runID string)
    List(parentSessionID string) []AgentRunSnapshot
}
```

调度限制(用户可配置)包括全局并发、单根 run 并发、单根 run Token 预算三项。默认全局/单根并发为 4,这是保守工程默认值而非性能结论。桌面设置通过 REST 热更新调度器并原子写入数据目录下的 `agent-limits.json`;手工编辑配置文件在内核重启后生效;文件不存在时使用 `FOYA_AGENT_MAX_GLOBAL_CONCURRENCY`、`FOYA_AGENT_MAX_PER_ROOT`、`FOYA_AGENT_MAX_TREE_TOKENS` 环境变量默认值。降低并发不会中断活跃任务,新任务会等待当前占用降到新上限。其它副作用工具仍保持顺序执行。

> 两项未暴露给用户的内部策略:
> 1. 递归深度:当前 Child Session 在 schema 和执行入口双重过滤了 `agent*` 派工工具,无法创建下一级 Child,深度物理上固定为 1。
> 2. 单根 run Child 总数:内核内部保留一个较大的安全上限作为「失控保险丝」,防止程序 bug 或模型循环让单任务无限创建 Child Session 与事件日志。该值由代码常量固定,用户配置和 API 均不能修改。

整棵根 run 共享 Token 预算。Engine 将每次模型 usage 回报给 Scheduler;超过 `max_tree_tokens` 后发布预算超限事件并取消该 run 的所有活跃 Child。父回合取消和删除父会话同样级联取消任务树。

Session、Event JSONL 和 Agent run 快照写入数据目录。内核重启后未完成 run 变为 `interrupted`;系统不会自动重放无法确认是否已产生副作用的工具。

后续需要持续协作时,可在现有 Child Session 上增加 `send_message`、`followup_task` 和持久邮箱;需要声明式工作流时再增加 DAG 控制面,不改变 Agent Loop 或 Session 执行模型。

## Computer Use(客户端侧能力)

职责:让 agent 操作屏幕。定义为工具集,但执行落在有 GUI 的客户端(Tauri Rust 主进程),内核只定义契约、反向调用。

```go
// 内核侧:只定义工具契约，不执行
type ComputerUseTool interface {
    Tool // click_element / type / screenshot ...(语义动作而非裸坐标)
}

// 内核通过 client capability 反向调用持有 GUI 的客户端
type ClientCapability interface {
    Invoke(ctx context.Context, conn ClientConn, action CUAction) (CUObservation, error)
}
```

咬合:内核侧工具收到调用 → 经 ClientCapability 反向 RPC 到 Tauri 客户端 → 客户端执行原生操作 → 截图作为 artifact 存储、事件只带引用。依赖 GUI 宿主,故属客户端侧能力。

## 记忆(Memory,上下文来源)

职责:保存对后续协作有价值的用户偏好、项目事实和经验。只支持全局与项目
两级作用域，属于参考上下文，不用于规范 Agent 行为。

```go
type MemoryStore interface {
    Get(scope Scope, projectID string) (Memory, error)
    Set(scope Scope, projectID, content string) (Memory, error)
    Append(scope Scope, projectID, fact string) (Memory, error)
    Clear(scope Scope, projectID string) error
}
```

咬合:ContextManager 每个模型步骤读取“全局 + 当前项目”记忆并在独立、
有预算的 `<foya_memories>` 区段中注入。用户可在客户端管理；Agent 仅通过
`memory_remember` 保存用户明确陈述或明确要求记住的信息。会话历史和
Compaction 仍是会话级上下文，不进入 Memory。

完整的数据模型、状态机、协议和安全边界见
[记忆功能架构](./记忆功能架构.md)。

## 技能(Skills,按需加载的指令包)

职责:把一类任务的专门指令打包,模型需要时才加载(省 token)。

```go
type SkillRegistry interface {
    List() []SkillMeta                                    // 只暴露 name+description(轻量)
    Load(ctx context.Context, name string) (Skill, error) // 按需拉全文
}

type Skill struct {
    Meta        SkillMeta
    Instruction string // 加载后注入上下文的指令
    Tools       []Tool // 技能可捆绑专用工具
}
```

咬合:List 的轻量描述常驻,Load 的全文按需注入(同工具的 Deferred 曝光思路);可通过一个 `skill` 工具让模型自己触发加载。技能是「上下文 + 可选工具」的打包。

Project 是 APP 管理的一等实体。`Project.ID` 是稳定身份，`Project.Path`
是可变的文件系统位置；Session 只保存 `project_id`，Agent、Terminal 和
Skills 在执行时通过 `Session.ProjectID -> Project.Path` 获取工作目录。
一个 Project 只绑定一个目录，但目录不是 Project 的身份或唯一键；多个
Project 可以绑定同一个目录，以承载不同的目标、会话和项目级配置。
删除 Project 只移除 Foya 中的项目记录，不删除磁盘文件；仍被 Session
引用的项目不能删除。

添加项目必须经过创建对话框：用户可填写项目名称并选择源文件夹，目录选择
本身不创建 Project，只有确认后才注册。名称为空时使用“新项目”。Session
允许不绑定 Project，此时工具和终端不获得项目工作目录。

发现目录分为两级:

- 全局技能:`~/.agents/skills`、`~/.foya/skills`
- 项目技能:`<Project.Path>/.agents/skills`、`<Project.Path>/.foya/skills`

同名技能按“项目高于全局高于内置”选择有效版本;同一层中 `.foya` 高于 `.agents`。项目 Skill ref 包含 Project ID，使不同项目的同名 Skill 启停状态相互隔离。管理界面保留各层记录并分组展示,模型只看到优先级解析后的有效技能。

## 命令(Commands,客户端触发的快捷动作)

职责:用户在客户端输入 `/xxx` 触发的预定义动作(如 /compact、/review、/clear)。是客户端交互层,不是模型能力。

```go
type Command interface {
    Name() string // "compact" / "review" ...
    Execute(ctx context.Context, args string, sess Session) (CommandResult, error)
}

type CommandRegistry interface {
    Match(input string) (Command, bool) // 解析 / 前缀
    List() []CommandMeta
}
```

咬合:客户端解析 `/` 前缀 → 经 REST 发对应指令 → 内核执行(有的转成 AgentLoop 的特殊 Turn,如 compact;有的纯客户端本地)。区别于工具:命令是人触发,工具是模型触发。

---

## 规则(Rules,常驻约束注入)

职责:用户明确制定的全局/项目行为约束，包括编码规范、语言与框架、禁止事项
和交互方式。Rules 由内核托管，Agent 不能自行修改。

```go
type RuleSet interface {
    List(scope Scope, projectID string) []Rule
    Create(scope Scope, projectID, content string) (Rule, error)
    Update(id, content string) (Rule, error)
    Delete(id string) error
}

type Rule struct {
    ID        string
    Scope     Scope // global / project
    ProjectID string
    Content   string
}
```

咬合:ContextManager 每次组装 Prompt 时，把“全局 + 当前项目”Rules 注入
独立 `<foya_rules>` 区段。项目 Rules 比全局 Rules 更具体。`AGENTS.md` 等
文件属于 Context Files 兼容层，不是 Foya Rules，也不是 Memory。全局
Rules 存于 `~/.foya/rules/user_rules.md`；项目 Rules 读取
`{project_path}/.foya/rules/*.md` 并以列表展示。

## 上下文来源三者的区分

Context Files、记忆、技能、规则容易混，必须按来源和权威区分：

| 节点 | 注入时机 | 来源 |
|---|---|---|
| Context Files | 启动或访问目录时加载 | `AGENTS.md` 等外部文件 |
| 规则 Rules | 每回合无条件注入 | 用户在 Foya 中制定 |
| 记忆 Memory | 每回合按 scope 有界注入 | 用户或 `memory_remember` |
| 技能 Skills | 模型/条件按需加载 | 打包的专门指令 |
